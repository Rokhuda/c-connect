# Project Brief — C Connect

## The problem statement given to candidates

> A pan-African technology group sells connectivity, data-centre space, energy and
> financial services to business customers. Today a customer deals with four different
> portals, four invoices and four support queues. Build **one** portal where a customer
> can buy, monitor and pay for everything — and build the cloud platform it runs on.

That framing is deliberately broad. Squads are expected to negotiate scope, not receive it.

## Personas

| Persona | Who | Needs |
|---|---|---|
| **Thandi** | IT manager at a 200-person logistics firm in Johannesburg | Order a second fibre link, see if it's installed, pay one invoice |
| **Kwame** | Ops lead for a fintech with racks in an Accra data centre | Check power draw, raise a remote-hands ticket at 2am |
| **Amara** | Finance manager | One statement across all services, in local currency |
| **Sipho** | Platform engineer at the group | Ship safely, know what broke, know what it costs |

## Scope

**In scope (v1, six sprints):**
- Web portal (responsive), REST/GraphQL API, PostgreSQL, event bus for cross-service updates
- Six product domains as separate services, one per software squad
- Cloud landing zone, Kubernetes runtime, CI/CD golden path, observability + cost visibility
- Synthetic data only, generated by seed scripts

**Explicitly out of scope:**
- Real payment rails — use a sandbox/stub provider
- Real customer data, real Cassava APIs, real branding assets
- Native mobile apps
- Multi-region active-active

## The stack — open source, end to end

A hard constraint: **every component is open source and self-hosted.** No proprietary
managed services. Candidates provision, configure, operate and debug the real thing
rather than clicking a console and hoping.

This is deliberate. A managed queue teaches you a console. Running your own teaches you
what a queue *is* — and that knowledge transfers to whatever a placement employer uses.

| Layer | Tools |
|---|---|
| Frontend | React or Svelte, TypeScript, Vite |
| Backend | Node/TypeScript, Python/FastAPI or Go — one per squad is fine, it forces contract-first integration |
| Data | PostgreSQL (+ PostGIS, pgvector), Valkey, TimescaleDB or VictoriaMetrics for telemetry |
| Object storage | MinIO |
| Messaging | NATS or Redpanda |
| Identity | Keycloak |
| Containers | Docker or Podman, Kubernetes (k3s or kubeadm) |
| IaC | OpenTofu |
| GitOps & delivery | Argo CD, Argo Rollouts, Helm |
| Registry | Harbor, with cosign signing and Trivy scanning |
| Ingress & network | Traefik, cert-manager, Cilium |
| Secrets | OpenBao with the External Secrets Operator |
| Policy | OPA and Conftest |
| Observability | Prometheus, Grafana, Loki, Tempo, OpenTelemetry, Alertmanager |
| SLOs | Sloth or Pyrra |
| Cost | OpenCost |
| Chaos | Litmus |
| Load testing | k6 |
| Developer portal | Backstage (optional, ticket CD-08) |

Squads may swap any of these — but only through an ADR that states what they gained
and what they gave up. "I preferred it" is not an ADR.

### Where it runs

Anywhere you can get plain Linux VMs: a low-cost European or African VPS provider,
university hardware, or refurbished machines in a room. The point is that nothing in
the stack depends on which one you pick. If your provider disappeared tomorrow, ticket
`LZ-04` means you could rebuild the whole environment somewhere else from code.

## DevOps is not a separate team

The four cloud squads build the platform. They do **not** operate the software squads'
services. Every software squad ships six DevOps tickets for its own service, labelled
`devops` on the board:

| Ref | Sprint | What the software squad owns |
|---|---|---|
| `D1` | 0 | Containerise their service — multi-stage, non-root, no baked-in secrets |
| `D2` | 1 | Write and own their CI pipeline, calling CL3's reusable workflow |
| `D3` | 1 | Own their Helm chart and deploy themselves via Argo CD |
| `D4` | 2 | Instrument with Prometheus metrics, Loki logs, Tempo traces, own Grafana dashboard |
| `D5` | 3 | Define and publish their own SLO and error budget |
| `D6` | 4 | Write their runbook and take an on-call shift during the game day |

The cloud squads provide golden paths, chart libraries, dashboards and office hours.
If a software squad has never seen its own deployment fail, the platform has been too
helpful and the ticket has not been done.

## Constraints candidates must design around

1. **Cost.** The programme has a fixed monthly cloud budget. CL4 publishes spend weekly.
   Squads that leave environments running overnight will see it on the dashboard.
2. **Bandwidth and latency.** Assume users on mobile networks with 200ms+ latency and
   intermittent connectivity. Payloads and offline behaviour matter.
3. **Multi-currency, multi-country.** ZAR, KES, NGN, GHS at minimum. No hard-coded currency.
4. **Data protection.** Model it against POPIA/GDPR principles — data minimisation,
   retention, access logging. Security review is part of Definition of Done.

## Success measures for the programme (not the product)

- Every candidate has merged PRs across at least two sprints
- Every candidate has reviewed someone else's code
- Every candidate has presented at a demo day
- The platform is deployed and reachable, with a runbook someone else could follow
- Each squad has at least two ADRs recording a decision and its trade-offs
